# Proposed OE Video Direction lesson: native tool legibility

**Status:** conditional candidate. Do not add it to the skill until r7 visually verifies the
native surface and readable crops. Do not treat it as a new global owner preference.

**Suggested location:** immediately after `### A workflow illustration is not a software
demonstration` in `.agents/skills/oe-video-direction/references/decision-method.md`.

> When a passage asks the viewer to trust that a named workflow tool is operating, show the
> native tool surface early. Then use intentional crop, zoom or a clearly editorial callout to
> direct attention to one readable node, control or state at a time at the delivery size. A custom
> operator form can follow to show human review, but labels that merely name the tool do not
> substitute for the native surface. Do not fabricate vendor UI or imply a graphical dashboard
> when the actual implementation used an API or request node. If the native surface is sensitive,
> unavailable or unreadable, disclose that limit and use another truthful proof rather than
> presenting a custom form as execution evidence.

**Why this is additive:** the existing section already requires real running software, actual
inputs, branches and outputs. This candidate adds the viewer-comprehension condition that r6
missed: actual execution can remain visually unproven if the native surface is never shown or the
important state is too small to read.

**Episode-specific exclusions:** do not carry EP009 frame numbers, Node-RED, OpenAI, the
fictional fixture, or the r6/r7 review status into the reusable skill text.
